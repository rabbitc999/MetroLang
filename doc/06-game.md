# 06 线网调度游戏

`metro-lang game` 把一份 `.metro` 编译成**自包含单文件游戏**：一个 HTML，里面
有数据、模拟内核、渲染层和 d3，双击就能玩，不联网、不读磁盘。

```sh
# 单文件游戏页
metro-lang game samples/guangzhou.m -o build/guangzhou-game.html

# 只要数据集（给 Node / 前端 / 离线算分用）
metro-lang game samples/guangzhou.m --json -o game/data/guangzhou.json

# 换标题
metro-lang game samples/guangzhou.m -o beijing.html --title "北京地铁 24 小时"
```

玩法是调度员视角：给每条线路定发车间隔、限速、跳站，撑过一天的高峰，最终按
准点率、满载率、平均等车时长和营收打分。

---

## 1. 为什么不让页面直接吃 JSON v2

v2（[02-json-format.md](02-json-format.md)）是**完整性优先**的交换格式，直接上
页面有三个问题：

| 问题 | v2 的写法 | 游戏要的 |
|---|---|---|
| 线路形状 | 每个方向各写一遍站序，`direction[].station[].next` 是到下一站的里程 | 一条**主链** + 若干**支线**，每段里程双向可查 |
| 体积 | 广州 ~380 KB | ~50 KB 才够每帧遍历 |
| 跨城重名 | 广州 2 号线与佛山 2 号线是两个独立 ID | 显示名不能撞 |

所以 `src/game_data.cpp` 做一次压平，产出 `format: "metro-game-1"` 的数据集。
`game/tools/prepare_data.py` 是同一件事的 Python 版，两条路**口径必须一致**，
`tests/test_game.py` 会交叉验证线路数与站数。

数据集用仓库自带的 [`json/`](../json/README.md) 库序列化（`json::Object` +
`dump()`），不手拼字符串——括号由库配对、字符串由库转义。这条规矩是从一次真实
事故来的：手拼 JSON 漏了一个 `}`，整个价格段被吞进上层数组，编译通过、页面上
白屏、控制台只有一句 `JSONDecodeError`。

## 2. 数据集结构

```jsonc
{
  "format": "metro-game-1",
  "source": "metro-lang game",
  "city": "广州",
  "version": "V1.0",
  "params": { "exit_time": 120, "inner_transfer_time": 300, "out_station_time": 900,
              "avg_board_time": 3, "dwell_default": 45, "reversal_time": 45,
              "accel": 1.0, "brake": 0.85 },
  "price": { "currency": "CNY", "default_fare": 2.0, "fare_cap": 0.0,
             "segments": [ { "rangeStart": 0, "rangeEnd": 4, "fare": 2 }, … ] },
  "transfer_types": { "SAME": { "name": "同台换乘", "time": 120, "status": "OPERATING" } },
  "stations": { "广州南站": { "lon": 113.2645, "lat": 22.9918, "city": "广州",
                              "lines": ["F2", "G2", "G7", "G22"] } },
  "lines": { "G12": {
      "id": "G12", "name": "12号线", "display": "12号线", "color": "#525813",
      "city": "广州", "formation": "6A", "maxspeed": 80, "capacity": 1860,
      "open_year": 2025, "special": false, "dwell": 45,
      "main":     { "stations": ["大学城南", …], "km": [2.09, 1.46, …] },
      "branches": [ { "stations": […], "km": […] } ],
      "future":   [ { "stations": ["二沙岛","东湖",…], "km": […] } ],
      "planned_only": false,
      "km_filled": []
  } },
  "headway": { "G12": [ [25200, 32400, 120.0], … ] },
  "crowd":   { "G12_0": [ [25200, 32400, 1.4], … ] },
  "stats": { "lines": 24, "branches": 3, "stations": 464, "stations_operating": 367,
             "line_stops": 459, "km_filled": 0, "future": 20, "planned_only": 3 }
}
```

要点：

- `lines` / `stations` / `headway` / `crowd` 都是**字典**（键为 id），C++ 侧靠
  `json::Object` 保持输入顺序。内核 `createGame` 会自己归一化成数组，不依赖调用方。
- `main.km` 长度恒为 `main.stations.length - 1`（[05-route.md](05-route.md) §6）。
- `headway` / `crowd` 的时段是 `[起秒, 止秒, 值]` 三元组，起止已转成**当天秒数**，
  跨零点时止点加一天（`22:00 → 06:00` 变成 `[79200, 108000, …]`），前端不必再解析
  `HH:mm`。
- `capacity` 按编组推定员：A 型 310 人/节、B 型 240、L 型 / 单轨 / 磁浮 200，
  `6A` = 1860 人。

## 3. 规划段与运营段（重点）

MetroLang 用 `FUTURE` 标记**尚未开通**的方向：

```metro
DIRECTION_DEFINE G12_4
    FUTURE
    STATIONS ['二沙岛', '东湖', '烈士陵园', '建设六马路', '麓湖', '中医药大学', '柯子岭', '景泰', '广州体育馆']
    DISTANCE AUTO
END_DEFINE
```

这个标记必须一路传到游戏里，否则会把没开通的轨道画成在跑车，而且页面看起来
完全正常——最难发现的那类错误。

### 3.1 三条规则

1. **`FUTURE` 方向不进 `main`、不进 `branches`**，单独落到 `lines[].future`。
2. **`future` 段不进内核的 `segments`**。调度、客流、指标全部遍历 `segments`，
   不进就是天然隔离，不需要在每处判断。
3. **整条线都在规划中**时（`G24` 只有 `FUTURE` 方向），线路**保留**并标
   `planned_only: true`。`main` 照填（保住线路实体与配色），但 `segments` 为空、
   不排车、不卖票。

第 3 条是踩过的坑：早期版本在 `chains.empty()` 时直接返回空，结果 `F24` / `F4` /
`F11` 这类纯规划线从数据集里整体消失——`stats.lines` 少 3 条、站点表少 97 站，
而页面上只是「少了一条线」，没有任何报错。

### 3.2 广州 12 号线：被规划段切断的线路

12 号线在数据里是三段平级的方向：

| 方向 | 站序 | `FUTURE` |
|---|---|---|
| `G12_0` | 大学城南 → 二沙岛 | — |
| `G12_4` | 二沙岛 → 东湖 → … → 广州体育馆 | **是** |
| `G12_1` | 广州体育馆 → … → 浔峰岗 | — |

产物是：

```
main:    大学城南 … 二沙岛            （9 站，运营）
branches: 广州体育馆 … 浔峰岗          （9 站，运营，与主链不相接）
future:   二沙岛 … 广州体育馆          （9 站，双向，规划）
```

`广州体育馆→浔峰岗` 与主链**确实不相接**——连接它们的中段还没开通。这不是数据
错误，是这条线的真实状态。测试把这种支线记为「待贯通」，不算失败但要报告：

```
· 24 条线路全部自洽；待贯通段 ['G12']（隔着规划段）；规划段 20 段已隔离
```

页面上规划段画成**虚线、35% 透明度**，玩家一眼能看出哪段在建。

### 3.3 站点表里的规划站

`stations` **包含**只在规划段出现的站（如 `东湖`、`烈士陵园`），因为画虚线需要
它们的坐标；但它们的 `lines` 是空数组——玩家到不了那里。所以：

- `stats.stations` = 站点表总条目（464，含规划站）；
- `stats.stations_operating` = 玩家能上下车的站数（367）。

页面标题显示后者，规划站数单独在 `stats.future` 里提示「N 段在建」。

## 4. 拼接：主链、支线与端点续接

`joinLine()` 把一条线路的所有方向压成「主链 + 支线」，顺序是：

1. **补缺失里程**。真实样例确有漏录（北京 1 号线 `福寿岭↔苹果园`、深圳 6 号线
   `松岗↔溪头` 的 `next` 为空，5234 个区间里共 4 处）。缺失值用**同线其余区间的
   中位数**顶上，并记进 `km_filled`。当 0 处理会让 `t = S/v` 算出 0 秒、列车瞬移。
2. **排除反向段**。数据里每条线正反各写一遍，`A→B→C` 与 `C→B→A` 是同一条轨道。
   不排除，下面的续接会让主链首尾相接、整条线重复两遍。
3. **选主链**：站最多；站数相同取里程长的。
4. **端点续接**：反复把「首站或末站等于当前链端点」的段接上去，直到接不动。
   - 这样 `G12` 那种三段平级的方向能拼成一条完整线路；
   - 续接要求「除接驳站外，别的站都不在主链里」。`G3` 的 `G3_1`
     （海傍→天河客运站）与主链 `G3_0`（海傍→机场北）**共享整段前缀**，
     不加这条会拼出 67 站、前半段重复两遍。
5. **剩下的才是支线**：过滤掉已覆盖站后的连续段，长度 ≥ 2 才算。
   段首/段尾各**多取一个已覆盖站当接驳锚点**——否则 `体育西路 — 石牌桥 — …`
   会变成一段悬空轨道，车不知道该从哪儿拐进去。

## 5. 模拟内核

`game/js/sim.js` 是纯函数 UMD 模块（浏览器 + Node 共用，不碰 DOM），
`game/test/sim.js` 直接 `require` 它跑测试。

- **帧驱动**：5 s 一帧，一天 05:00–23:30 共 84600 s。
- **绝对时刻状态机**：列车记 `t0` / `departAt` / `dwellUntil`，不是「走一格算一格」，
  所以改发车间隔不会让已有列车漂移。
- **区间耗时**按 [03-travel-time-model.md](03-travel-time-model.md) §6：
  `t = S/v_max + v_max/2 × (1/a_acc + 1/a_brake)`，`a_acc = 1.0`、`a_brake = 0.85`。
- **可复现**：xorshift32 + `seed`，同 seed 两次跑出逐字节相同的结果。
- **车队规模**按**高峰**发车间隔算：`ceil(roundTrip / peakHeadway) + 1`。按平峰算
  会严重低估（广州从 756 列掉到 403 列），结果全城平均等车 24 分钟。
- **首班车按相位均匀铺车**（`phase = i × headway`），不是堆在两端——堆在两端会
  让发车瞬间出现几十列车同时出发。
- **满载率**口径是**最大断面高峰满载率**（运营报表口径），不是全线平均。平均算
  出来只有 1%–7%（看着像没客流），断面口径能到 19%–96%，可玩。
- **等车时长**按段累加 `p.waited`，**不含乘车时间**。早期用「到站时刻 − 进站时刻」
  把乘车时间也算进去，平均等车虚高到 1463 s。
- **换乘**只认「换过去能直达目的站」的线路，且本线能直达就不下车。条件太松会
  让乘客在车上反复倒手（人均 0.87 次换乘）。

广州样例（seed = 1）的基线指标：

```
发车 6160 班 · 缺车 27 次 · 进站 105 万人 · 平均等车 378 s
最大断面满载 78% · 准点率 100% · 评分 87
```

## 6. 前端

`game/js/ui.js`（视图）+ `game/css/style.css`。

- **三栏布局**：左控制台（发车间隔 / 限速 / 跳站）、中线网、右线路榜，底部时间轴。
- **一次性建 DOM**：367 站、6000 多个区间点、900 多列车，每帧重建会直接卡死。
  只在开局建一次，之后按 `tr.id` 复用节点、只改 `cx/cy`。
- **投影**：墨卡托等比（按 `cos(lat)` 校正），`d3.line().curve(d3.curveCatmullRom)` 画线。
- **投影用站表**比运营站表多一类：规划段独有的站。不带上它们，虚线会断成几截。
- **只画换乘站圆点**：单线小站全画出来会糊成一片。

### 6.1 缩放与平移：动 `viewBox`，不动 `transform`

相机是 `{ k, cx, cy }`，`applyCamera()` 把视口写成
`viewBox = "cx - W/2k, cy - H/2k, W/k, H/k"`。

之所以用 `viewBox` 而不是 `g.attr('transform', 'scale(k)')`：`transform` 会把线宽、
站点点半径、文字一起放大，放到 8 倍时线粗得像色块。写 `viewBox` 相当于换镜头，
`stroke-width` 和 `r` 仍按屏幕像素算，视觉恒定。代价是字号不再跟着自动缩放，
得自己按 `1/k` 反算——这正是下一节要解决的。

| 交互 | 行为 |
|---|---|
| 滚轮 | 1.15× 步进，以光标为锚点 |
| 拖拽 | `pointerdown/move/up`，退出时统一 `releasePointerCapture` |
| 双击 | 复位全图 |
| 右下角控件 | `+` / `−` / `⤢` / `Aa` |
| 键盘 | `+` `-` `0`（复位）`L`（切标签） |

锚点不漂移靠这一行：`ratio = cam.k / next`，让视口尺寸按比例反算，而不是把屏幕
坐标直接当画布坐标用。测试里专门量了「缩放后锚点对应的视口位置仍是原像素」。

`k` 上限 12。再往上是纯像素噪声：线宽恒定而站距放大，只会看到一堆直线。

### 6.2 站名标签：按 `1/k` 反缩放 + 贪心避让

参考的是 VSCode 插件里那套做法——标签字号随缩放**反向**变化，视觉上一直是同一个
大小，同时只显示放得下的那些。

```js
var size = Math.max(LABEL_MIN, Math.min(LABEL_MAX, LABEL_BASE / cam.k));
```

- `LABEL_BASE = 9`：`k = 1` 时全图 9px（约等于 900×640 画布上的合理密度）。
- 放大到 `k = 4` 时算出来 2.25，低于 `LABEL_MIN = 3.2`，**被下限夹住**。
  这是有意的：真按 `1/4` 缩，屏幕上字只有 2px，糊成灰点还不如不显示。
  所以「屏幕大小恒定」只在 `k ≤ 2.8` 成立，之后退化为「字号贴地下限、露出更多站」。
  测试断言也得照这个口径写，否则会误判成 bug。
- 描边 `stroke-width = max(0.6, 2.2 / cam.k)`，`paint-order: stroke` 先描边后填字，
  压在彩色线路上也读得清。

避让是贪心的：先按 `rank` 排序（**换乘站 3，普通站 1**），逐个试放，与已放下的
标签屏幕矩形相交就 `display: none`。只对落进当前视口的站做这件事——全图 464 个站，
视口内通常只有几十个，避免每帧 O(n²)。

换乘站优先的结果是：缩到全图时看到的基本都是换乘枢纽名，放大后小站才陆续冒出来，
和看纸质线路图的习惯一致。

## 7. 测试

```sh
# 内核（纯 Node，不需要浏览器）
node game/test/sim.js

# 前端（jsdom，没有 jsdom 就跳过、退出码 0）
node game/test/ui.js

# 数据集契约 + 与 Python 管线交叉验证
python tests/test_game.py --bin build/metro-lang/metro-lang

# 三者都在 make 里
mingw32-make game-test
```

`game/test/ui.js` 用 jsdom 真把 SVG 建出来量属性。这一层的 bug 全是「不报错但
看不见」：`normalize()` 把 `stations` 字典转成数组，`View` 按站名索引全部拿不到
坐标，于是静默掉进网格兜底——线网糊成一团乱麻，控制台一句错都不报。纯读代码
发现不了，只能真的挂上 DOM 去量 `viewBox`、路径里的坐标、标签的 `font-size`。

覆盖 23 项：挂载、`viewBox` 由相机驱动、路径里是真实经纬度（不是网格兜底）、
标签节点数与可见数、坐标与字号有限（`NaN` 会让整层消失）、4× 缩放的视口、
百分比文案、字号随 `k` 单调变小、锚点不漂移、上限、复位、开关按钮两态。

几个坑记一下：`window` 里挂的是 `MetroSim`（不是 `sim`）；必须
`runScripts: 'dangerously'` 再注入 `<script>` 才能执行 `ui.js`；jsdom 的
`readyState` 停在 `loading`，得手动补派 `DOMContentLoaded`。jsdom 不完整支持
`WheelEvent`，所以缩放测试直接调 `view.zoomAt()`，不模拟滚轮。

`tests/test_game.py` 把数据集当**协议**测，分十组：

| 组 | 查什么 |
|---|---|
| JSON 可解析 | `--json` 输出必须是合法 JSON（历史事故的回归） |
| 顶层结构 | 12 个顶层键齐全，`format` 正确 |
| 参数表 | 8 个参数键齐全且为正 |
| 票价阶梯 | 区间递增、票价非降、首段从 0 起 |
| 统计对账 | `stats` 各项与实际内容逐一相等 |
| 线路里程 | `km` 长度 = 站数 − 1、里程全正、支线有接点、规划段不重叠 |
| 发车间隔 / 拥挤度 | 三元组格式、秒数落界、值不低于下限 |
| 线网连通 | 从任一换乘站出发能走遍所有运营线路 |
| Python 交叉验证 | 同一份 `.metro`，C++ 与 `prepare_data.py` 的线路数 / 站数相等 |
| 单文件 HTML | 无外链、内嵌数据集可解析、`</` 已转义、`--title` 生效 |

补里程、待贯通段、规划段数都会在汇总行里报出来，不藏。

## 8. 已知边界

- **`MERGE` 不生效**：`samples/guangzhou.m` 末尾的 `DIRECTION_DEFINE G12_0 G12 /
  MERGE G12_3 G12_5` 这类重定义式合并没有真正合并（`G12_0` 仍是 9 站）。
  这是编译器的独立问题，不影响游戏——`joinLine` 的端点续接已经能把平级方向段
  拼成完整线路，所以游戏侧看到的是正确形状。
- **`DIRECTION_TEMPLATE` / `IS_FUTURE` 模板级标记**尚未在游戏侧识别，只认方向级
  的 `FUTURE` 关键字。
- **事件系统**（随机故障、突发大客流）尚未实现。
